# 猜猜我（guess-me）· MVP v3

一个无账号、无后端的双人"自答 + 互猜"小游戏。

## 玩法流程

系统从内置精选题库随机抽取 5 道题 → A 先选出自己的真实答案 → 生成链接发给 B → B 猜 A 的 5 个答案 → B 再从题库抽取 5 道不同题并选出自己的答案 → 生成返回链接 → A 猜 B 的答案 → 双方结果在本页本地揭晓。

玩家不需要自己编写题目。

## 链接协议（protocolVersion 3）

URL Fragment 只携带状态，不携带题目文字：

```json
stage1（A→B）: { "pv":3, "bv":1, "st":1, "g":"6位对局ID", "q":["5个题目ID"], "aa":[5个答案索引] }
stage2（B→A）: { "pv":3, "bv":1, "st":2, "g":"同上", "q":[...], "aa":[...], "bq":["B的5个题目ID"], "bg":[B对A的猜测], "ba":[B自己的答案] }
```

- 题目与选项文字由打开方从本机加载的 question-bank.js 按 ID 还原，不进 URL。实测链接：A→B 约 160 字符、B→A 约 300 字符（整条 URL），便于微信内完整复制。
- `pv`=协议版本，`bv`=题库版本，相互独立。改 payload 结构升 pv；改题目文字/选项/增删题必须升 `QUESTION_BANK_VERSION`（见 question-bank.js 头部）。版本不匹配的旧链接会被明确拒绝（fail-closed），不会静默变脸。
- `g` 为对局标识，仅用于状态归因与排错，不承诺一次性防重放。
- 校验规则（任一失败进入错误页，内部有独立错误码 ERR_*，界面统一文案）：pv/bv 匹配、st∈{1,2}、g 格式、题目 ID 必须存在于题库、两组题不重复、答案均为 0..3 整数、题数恰为 5。

## 题库

内置 81 道题，分为 9 类（行为/反应/决策/假设/社交/兴趣/习惯/相处/刁钻），每类 9 题。每局从 5 个不同类别各随机抽 1 题；B 的 5 题会排除 A 已用的题目 ID。

题库不预设"正确答案"。"正确答案"就是玩家自己选择的、最符合自己的选项。

题库设计原则：避免模板化情侣问卷、避免纯个人资料题、避免语义重复；四个选项都保持合理性，让"猜"本身有意义。题目 ID 一经发布不复用、不改义；废弃题目只升版本号或改文案，不物理删除 ID。

## 隐私与威胁模型（如实声明）

- 游戏程序不发起网络请求，不使用后端、数据库、账号、广告、统计或第三方 SDK。
- 游戏状态只通过 URL Fragment 和运行时内存传递；不使用 Cookie / localStorage / sessionStorage / IndexedDB。
- **"不会上传"仅指游戏程序本身**：GitHub Pages 只分发静态文件，URL Fragment 不会发送给服务器。
- **Fragment 里的答案对任何拿到链接的人可解码**。Base64URL 只是编码，不是加密。链接会留在聊天记录里；请把链接只发给想一起玩的人。这是本游戏的公开威胁模型：防顺手翻看，不防有心人解码。
- 若需要更强的"猜前不可见"，必须引入口令/服务器，属于产品形态变更，不在 MVP 内。

## 技术

Vanilla HTML/CSS/JS，无构建、无依赖。静态资源以 `?v=3` 钉版引用，配合发布节奏避免新旧混合缓存。

## 版本历史

- v1：玩家手动互出题（已废弃）。
- v2：改为内置题库随机抽题+互猜；URL 携带完整题目文字。
- v3（当前）：URL 精简为题目 ID 协议（pv/bv/g/状态），加入题库版本号、ID 存在性与重复校验、内部错误码、资源钉版。旧 v2 链接不再兼容，打开会进入错误提示页。
